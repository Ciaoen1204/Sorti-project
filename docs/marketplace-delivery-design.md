# 市集寄送方式與收件流程設計

日期：2026-10-11。狀態：使用者已核准，兩端下拉選單及相容 SQL 已實作；雲端 SQL 待使用者執行。

## 配色與平台

Android 與 PWA 都延續首頁主題，淺色使用白色卡片、深色文字及既有主色按鈕；尊重使用者深色設定。選取方式以勾選、邊框與文字呈現，不只依靠顏色。保留既有三步刊登、獨立聊天、賣家交付與買家收貨流程。

## 賣家刊登：第三步「交易方式」

面交與寄送可同時提供。使用下拉選單選擇面交、7-ELEVEN、全家、萊爾富、OK 超商、宅配；按「新增交易方式」可提供另一個不重複的管道。這些代表賣家承諾自行安排的管道，不代表平台已串接物流服務。

每張卡片依序顯示管道下拉選單，以及選取後展開的「運費 NT$」和「寄送說明（選填）」。運費必須明確填寫非負整數，0 顯示免運；移除方式後不提交該管道。至少選取面交或一種寄送管道。

畫面範例：

```text
交易方式                         可複選
☑ 面交
  面交區域：高雄市大社區
  說明：地點與時間請透過聊聊約定

☑ 提供寄送
  ☑ 7-ELEVEN  運費 NT$ [賣家填寫]
  ☑ 全家      運費 NT$ [賣家填寫]
  ☐ 萊爾富    ☐ OK 超商    ☐ 宅配

[查看刊登預覽]                 [確認刊登]
```

不預填官方價格或暗示固定尺寸、配送時間、貨到付款支援。提示賣家先確認所使用服務可承運商品及目前費用。僅選面交時不顯示寄送欄位。

## 商品詳情

交易方式卡列出面交及每種可用管道、對應運費和寄送說明。例如「全家 · 運費 NT$［賣家設定金額］」。購買入口進入選擇流程，聊天依舊開獨立聊天室。

## 買家下單

順序：確認商品 → 選取交付方式 → 填收件資訊 → 確認總額與送出購買請求。只提供商品有開放的管道，不自動替買家選不同管道。

| 方式 | 收件欄位 | 不顯示欄位 |
|---|---|---|
| 面交 | 無；接單後聊聊約時間地點 | 收件人、電話、門市、地址 |
| 四家超商 | 收件人姓名、手機、門市名稱、店號、門市地址 | 宅配收件地址 |
| 宅配 | 收件人姓名、手機、收件地址 | 超商门市 |

門市先採手動填寫，顯示「請確認門市名稱、店號及地址正確」。不偽造門市搜尋或驗證能力；未接服務商前不稱已驗證門市。手機輸入保留前導 0，兩端共享驗證。運費與商品金額都以伺服器驗證及訂單快照為準。

購物車依「賣家＋交付管道＋收件目的地」分組；同賣家不同管道不得混成一筆。只有全部商品都開放同一管道時才提供合併選項。為延續現有規則，同組運費取商品中最高運費；畫面在送出前清楚列出每組商品小計、運費及合計。商品或管道設定改變時要求重新確認，不悄悄替換或加價。

## 出貨與完成

訂單保留買家選定的管道與收件資訊快照，後續修改商品設定不影響成立訂單。寄送畫面首先顯示管道、收件人、手機和門市／地址，並提供複製資訊操作。

寄送：等待賣家接單 → 待出貨 → 賣家實際寄出並填寫寄件日期、實際物流服務／單號及選填備註 → 已出貨、待買家收貨 → 買家確認收到 → 完成。超商品牌與實際承運服務分開儲存；不將品牌名稱當成物流串接或付款狀態。無物流查詢 API 時只顯示「賣家提供的寄件資訊」。

面交：等待接單 → 聊聊協商 → 賣家確認交付 → 買家確認收貨 → 完成。沿用目前取消協商、問題協調及角色限制。

## 資料與相容方案（待實作確認）

目前只有 meetup／shipping 與單一 shipping_fee。建議保留 delivery_method 的面交／寄送大類，另新增管道資料，避免破壞既有狀態機。

- 刊登管道：固定識別 seven_eleven、family_mart、hi_life、ok_mart、home_delivery；各自包含運費與說明。
- 訂單快照：selected_shipping_channel、管道名稱、運費、收件類型與結構化門市資訊；既有姓名、電話、地址欄位保持相容。
- RPC 必須檢查管道確實由賣家提供、費用正確、收件欄位符合方式；訂單保留與版本檢查不改。
- 收件資料僅允許交易雙方讀取，禁止出現在公開商品、賣家頁或通用聊天預覽。
- 舊訂單繼續顯示「一般寄送」並沿用原有地址；舊商品不得自動被標記支援四家超商，賣家可編輯补充。
- 所有資料操作集中 supabaseData.ts，PWA 由 pwa:prepare 匯出。SQL 採追加欄位與相容更新，不刪除歷史資料；實作前呈現具體 migration 與交易規則供使用者確認。

## 驗收重點

兩端可完成上架、編輯、各方式下單及角色出貨收貨。驗證多管道不同運費、門市／宅配欄位切換、面交免收件資訊、多賣家分單、設定變更與重試、舊商品／訂單、錯誤保留輸入。型別檢查與適當功能測試後重新打包 PWA；Native 有修改則產生 APK。

## 實作與部署

已實作檔案：deliveryChannels.ts 共用管道／驗證、Native DeliverySelect、PWA DeliveryOptions、兩端刊登／下單／商品／訂單詳情；資料層仍集中 supabaseData.ts。SQL 為 supabase/marketplace-delivery-channels.sql，保留 meetup/shipping 大類與已核准交付流程，新增 delivery_options、shipping_channel、pickup_store。舊商品由賣家編輯時明確重選管道；舊訂單沿用一般寄送。每次下單同一超商品牌共用一組門市資料，不提供同品牌多目的地；不同品牌、宅配可在同次請求分單。尚未接入物流商或門市 API。
